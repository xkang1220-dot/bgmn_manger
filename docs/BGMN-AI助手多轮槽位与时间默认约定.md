# BGMN AI 助手 — 多轮槽位填充与时间默认约定（后端）

> 面向后端 Agent / `normalize_time_range` / 草稿组装  
> 协议版本：`1`  
> 关联：[确认卡片与文案约定](./BGMN-AI助手确认卡片与文案约定.md)、[前端联调说明](./BGMN-AI助手前端联调说明.md)

---

## 1. 问题与目标

当前体验问题（需后端改行为，前端无法兜底）：

1. 用户说「早上九点半到现在」「今天 09:00 到 11:00」仍反复失败或要求换说法。  
2. 上一轮已确认项目为 ERP，用户只回「早上…」或只回新项目名时，系统不合并上下文，要求整句重说。

**目标**：多轮对话按**槽位（slot）**累加；时间能默认则默认；缺参优先补槽，**能出确认卡片就出卡**，由用户在卡片上改，而不是反复追问精确格式。

---

## 2. 记工槽位（Session Draft）

每个会话维护一套进行中的记工草稿槽位（可多条任务，每条独立一套）：

| 槽位 | 字段 | 说明 |
|------|------|------|
| 项目 | `projectId` / `projectName` | 可经 `resolve_project`；多命中才 `clarify` |
| 时间 | `startAt` / `endAt` | 由确定性时间解析器写入 |
| 事项 | `title`（+可选 `content`） | 具体做了什么 |
| 状态 | `status` / `statusLabel` | 缺省可按语境建议，默认「已完成」或「待办」见下 |

### 2.1 短回复合并规则（强制）

用户当轮若是**短回复**（通常 ≤ 20 字，或仅为专名/时段短语），必须先尝试填入**当前未满槽位**，禁止当成「全新记工」且丢掉上文。

| 用户当轮说法示例 | 正确行为 |
|------------------|----------|
| `ERP` / `ERP 客户端` | 写入/覆盖项目槽；其他槽保留；若其余已齐 → 出 `confirm_card` |
| `早上` / `上午` / `上班` | 写入时间槽（按第 3 节默认），**不要再追问**「请给具体到分钟」 |
| `09:00 到 11:00` / `今天 09:00 到 11:00` | 写入时间槽；合并已有项目/事项 |
| `修登录 bug` / `客服模块线上问题` | 写入事项标题槽 |
| `已完成` / `还在做` | 写入状态槽 |

**错误行为（禁止）**：

- 「请用『今天 09:00 到 11:00』这种格式再说一遍」——在已能解析或可默认时。  
- 用户已说项目名后，又要求「请完整描述：项目+时间+事项」。  
- 工具失败时回「暂时无法完成该请求，请换一种说法」而不尝试默认时间或合并上下文。

### 2.2 出卡门槛（放宽）

满足下面即可出 `confirm_card`（`pendingConfirm=true`），不必四槽「用户逐字确认」：

1. **项目**已解析到唯一 `projectId`（或 clarify 已选）；并且  
2. **事项** `title` 非空；并且  
3. **时间**已有 `startAt`/`endAt`（含默认填充）。

状态缺失时：

- 语境含「做了 / 处理了 / 完成了 / 弄完了」→ 默认 `status=2` 已完成；  
- 含「正在 / 排查中 / 还没做完」→ `status=1`；  
- 否则默认 `status=0` 待办。  

时间或标题略含糊时：**用合理默认写入卡片**，旁白最多一句「请确认时间与事项」，让用户在卡片上改。

仅在以下情况追问（短 `markdown` 或 `clarify`，一次只问缺的那一项）：

- 完全没有项目线索，且无法从上下文继承；  
- 完全没有事项标题；  
- 项目名多命中（必须 `clarify`）；  
- 时间表达无法映射到任何规则且无法给默认（极少见）。

## 3. 时间默认表（确定性，优先于模型）

实现位置：`normalize_time_range`（或等价服务）。锚点：`Asia/Shanghai` 的 `now`。  
**原则：能默认就默认，写入卡片让用户确认；禁止因「不够精确」反复询问。**

### 3.1 常用短语

| 用户表达（含近义） | 默认区间 | 说明 |
|--------------------|----------|------|
| 早上 / 早晨 / 一早 | 当日 `09:30:00` ~ `12:00:00` | |
| 早上上班 / 上午上班 / 上班（上午语境） | 当日 `09:30:00` ~ `now`（若 now&lt;09:30 则 ~12:00） | 「上班」无下午语境时按上午 |
| 上午 | 当日 `09:30:00` ~ `12:00:00` | |
| 中午 | 当日 `12:00:00` ~ `13:30:00` | |
| 下午 / 下午上班 | 当日 `13:30:00` ~ `18:00:00` | |
| 晚上 | 当日 `18:00:00` ~ `21:00:00` | 可配置 |
| 今天 / 今天一天 | 当日 `09:30:00` ~ `min(now, 18:00:00)` | |
| 过去一小时 / 刚才一小时 | `now-1h` ~ `now` | |
| 到现在 / 至今 | 起点按上文或默认早上 `09:30`，终点 `now` | 见 3.2 |
| `HH:mm` 到 `HH:mm` / `今天 HH:mm 到 HH:mm` | 当日对应时刻 | **必须能解析**，禁止失败后让用户重说 |

工作日上班默认起点统一为 **09:30**（不是 09:00），与产品约定一致。

### 3.2 「X 到现在」

| 说法 | 起点 | 终点 |
|------|------|------|
| 早上九点半到现在 / 9:30 到现在 | 当日 09:30 | now |
| 早上到现在 / 上午到现在 / 上班到现在 | 当日 09:30 | now |
| 下午到现在 | 当日 13:30 | now |
| 过去两小时到现在 | now-2h | now |

### 3.3 解析失败时

1. 先套默认表与正则；  
2. 仍失败 → **不要**只回「暂时无法完成」；改为一次短追问：「时间是早上、上午还是具体几点到几点？」并给出例子；  
3. 若项目+事项已齐、仅时间失败 → 可默认「今天 09:30 ~ now」出卡，旁白：「时间暂按今天上班至今，请在卡片中核对」。

### 3.4 对用户可见的时间文案

- 卡片用 `timeLabel`（如同日：`09:30:00 ~ 11:20:00`）。  
- `markdown` 不要写「当前服务器时间是…所以过去一小时即…」。  
- 需要提及时只写：`时间：09:30:00 ~ 11:20:00`。

## 4. 多轮对话策略（Agent / Prompt 约束）

1. **始终读取本 session 历史与当前 draft 槽位**，再决定追问还是出卡。  
2. 用户纠正某一槽（如换项目名）→ **只更新该槽**，立刻尝试 `draft_log_tasks` 出卡。  
3. 同一轮不要既说「已确认项目 ERP」又要求用户把整句重说一遍。  
4. `clarify` 选完 option 后，用 `optionId` 写槽，合并历史，继续推进，而不是重置会话。  
5. 工具报错（如时间格式）在服务层吞掉并改用确定性解析；对用户禁止暴露工具名与异常栈。  
6. 单次用户消息后，追问最多 **1** 个缺失槽；能默认则不出追问。

### 4.1 推荐状态机（简）

```text
收到 user message
  → 抽取/合并槽位（短回复优先填空槽）
  → 时间短语走 normalize_time_range（含默认表）
  → 项目模糊 → resolve；多命中 clarify；0 命中短追问项目
  → 若 project + title + time 齐 → confirm_card
  → 否则只追问仍空且无法默认的那一项
```

### 4.2 对话示例（期望）

**例 A — 短回复补时间**

1. 用户：帮我登记，项目 ERP，做了 AI 助手功能  
2. 助手：还差时间，是早上、上午还是具体几点到几点？  
3. 用户：早上九点半到现在  
4. 助手：直接 `confirm_card`（09:30 ~ now，项目 ERP，事项 AI 助手…）  
   - 禁止：再要求「请用今天 09:00 到 11:00 格式」

**例 B — 只回项目名纠错**

1. 上下文已有时间与事项，项目误匹配  
2. 用户：ERP  
3. 助手：更新项目为 ERP，其余槽保留 → `confirm_card`  
   - 禁止：要求用户再说「今天几点在 ERP 做了什么」

**例 C — 早上默认**

1. 用户：今天早上在 ERP 处理了线上问题  
2. 助手：时间按 09:30~12:00（或到 now 若仍是上午）出卡  
   - 禁止：追问「早上具体是几点」

## 5. 验收用例（给后端自测）

| # | 步骤 | 期望 |
|---|------|------|
| 1 | 「今天早上在 ERP 做了线上问题，已完成」 | 一次出卡；时间含 09:30 起点；无反复追问 |
| 2 | 先「登记 ERP 的 AI 功能」再「早上到现在」 | 第二轮合并出卡，不丢项目/事项 |
| 3 | 草稿项目不对，用户只回「任务系统」 | 覆盖项目后出卡或更新卡，不要求整句重说 |
| 4 | 「今天 09:00 到 11:00」 | 必须解析成功；禁止「暂时无法完成，请换说法」 |
| 5 | 「上班」+ 已有项目事项 | 09:30 起点默认出卡 |
| 6 | 可见文案 | 无服务器当前时间推导长句；无工具失败原文 |

## 6. 配置建议

可将默认表做成配置（避免写死在 prompt）：

```yaml
kk:
  ai:
    work-time:
      morning-start: "09:30"
      morning-end: "12:00"
      afternoon-start: "13:30"
      afternoon-end: "18:00"
```

`normalize_time_range` 只读配置；LLM 不得擅自改默认表。

## 7. 与前端的分工

| 职责 | 方 |
|------|----|
| 槽位合并、时间默认、出 `confirm_card` | **后端** |
| 渲染卡片、用户改时间/标题后 `confirm` | 前端 |
| 用户点澄清选项回传 `clarifyAnswer` | 前端已支持 |

前端不会在本地猜时间默认；本约定全部由后端落实。
